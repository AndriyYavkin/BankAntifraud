# 5. Пояснення коду

Код не містить коментарів за вимогою завдання, тому пояснення зібрано тут.

## auth-service (`services/auth-service/Program.cs`)

| Частина | Що робить |
|---|---|
| `UserStore` | таблиця `users` у SQLite: створення, пошук, вмикання та вимикання користувачів |

| `POST /register`, `/users/*` | доступні лише ролі `admin` через `RequireRole("admin")` |
| Метрики | `bank_auth_login_attempts_total{result}`, `bank_auth_tokens_issued_total{role}` |

### TransferExecutor.ExecuteAsync

1. Перевіряє наявність рахунків, суму (більше 0, не більше 1 000 000, до 2 знаків після коми), різні рахунки.
2. У циклі спроб викликає `RunTransactionAsync`.
3. `PostgresException` з `SqlState` `40P01` (deadlock) або `40001` (serialization failure): записує метрику конфлікту, лог із текстом PostgreSQL, подію в трейс. Якщо спроби залишились, чекає 20–120 мс і повторює, інакше повертає 409.
4. Помилка з'єднання або SQLSTATE класів `57P`, `08`: 503 `database_unavailable`.
5. Після успішного COMMIT записує метрики, лог і публікує подію.

### TransferExecutor.RunTransactionAsync

```
BEGIN ISOLATION LEVEL <рівень>
SELECT id, balance, currency, is_blocked FROM accounts WHERE id = <перший> FOR UPDATE
(пауза X-Lock-Hold-Ms)
SELECT ... WHERE id = <другий> FOR UPDATE
перевірки → ROLLBACK і 4xx, якщо не виконано
UPDATE accounts SET balance = balance - сума WHERE id = A RETURNING balance
UPDATE accounts SET balance = balance + сума WHERE id = B RETURNING balance
INSERT INTO transfers (...)
COMMIT
```

| Режим | Порядок блокування | Навіщо |
|---|---|---|
| `ordered` | менший id, потім більший | робочий режим, deadlock неможливий |
| `naive` | спочатку відправник, потім отримувач | демонстрація deadlock |
| `none` | без `FOR UPDATE`, баланс записується як обчислене в коді значення | демонстрація втраченого оновлення і роботи `SERIALIZABLE` |

`await using` для з'єднання і транзакції гарантує ROLLBACK, якщо транзакцію не зафіксовано.

### EventPublisher.PublishAsync

1. Створює спан `bank publish` (тип Producer).
2. Записує `traceparent` у заголовки AMQP через `Propagators.DefaultTextMapPropagator.Inject`.
3. Під `SemaphoreSlim` використовує один канал з увімкненими publisher confirms; `BasicPublishAsync` завершується після підтвердження брокера.
4. При помилці закриває з'єднання, щоб наступна публікація підключилась заново, і повертає `false` (метрика `bank_events_published_total{result="failed"}`).

| Файл | Що робить |

### FraudConsumer.HandleAsync

1. Відновлює контекст трейса з заголовків, створює спан `transfers.fraud-check process` (тип Consumer) з батьком із transfer-service.
2. Розбирає JSON. Помилка формату: `BasicNack(requeue: false)`, RabbitMQ переносить повідомлення в `transfers.invalid`.
3. Викликає `FraudAnalyzer.AnalyzeAsync`.
4. `Duplicate`: лише ack. `TransferMissing`: nack без повтору. `Whitelisted`: ack.
5. Помилка бази: пауза 2 с і `BasicNack(requeue: true)`, подія не губиться.

### FraudAnalyzer.AnalyzeAsync

1. `SELECT fraud_status FROM transfers WHERE id = ... FOR UPDATE`: якщо не `pending`, подія повторна. Блокування рядка не дає sweeper-у і споживачу обробити переказ одночасно.
2. Якщо обидва рахунки внутрішні, позначає `clean`.
3. Правила `high_amount`, `round_amount`, `balance_drain` рахуються з самої події.
4. Один SQL-запит з `count(*) FILTER (...)` рахує перекази за вікнами часу для `velocity`, `fan_out`, `ping_pong`. Вікна відраховуються від `created_at` переказу, а не від поточного часу.
5. Записує алерти, оновлює `fraud_status`, `fraud_score`, `checked_at`, за потреби блокує рахунок. Усе в одній транзакції.

## load-generator (`services/load-generator/Program.cs`)

Консольна програма з функціями `NormalAsync`, `FraudAsync`, `DeadlockAsync`, `LostUpdateAsync`, `InvalidAsync`, `UnauthorizedAsync`, `SeedAsync`, `MixedAsync`. Кожен переказ виводиться рядком із кодом відповіді та часом; наприкінці друкується зведення за кодами та p50/p95 затримки. `LostUpdateAsync` порівнює загальну суму гривень до і після.

# 8. Аналіз і архітектурні рішення

## Що спостерігаємо в системі

Тема вимагає спостерігати тривалість транзакцій, deadlock-и при зустрічних переказах і помилки валідації балансу. Нижче, де це видно і чому саме так.

| Що | Метрика або джерело | Панель дашборда |
|---|---|---|
| Тривалість транзакцій | `bank_transfer_tx_duration_seconds{isolation, lock_mode, outcome}` | «Transaction duration p95 by isolation / lock mode» |
| Найдовша відкрита транзакція | `pg_stat_activity_max_tx_duration` | «Longest open transaction» |
| Deadlock-и (застосунок) | `bank_transfer_conflicts_total{type="deadlock"}` | «Conflicts per minute» |
| Deadlock-и (СУБД) | `pg_stat_database_deadlocks` | «PostgreSQL deadlocks, commits, rollbacks» |
| Деталі deadlock-у | журнал PostgreSQL у Loki: `ERROR: deadlock detected`, `DETAIL: Process ... waits for ShareLock ...` | «PostgreSQL deadlocks and lock waits» |
| Блокування | `pg_locks_count{mode}` | «PostgreSQL locks by mode» |
| Конфлікти серіалізації | `bank_transfer_conflicts_total{type="serialization"}` | «Conflicts per minute» |
| Помилки валідації балансу | `bank_transfer_validation_errors_total{reason}` | «Balance validation errors» |
| Цілісність грошей | `bank_total_balance` | «Total amount of money (consistency check)» |
| Шахрайство | `bank_fraud_checks_total`, `bank_fraud_rule_hits_total` | розділ «Anti-fraud» |
| Шлях одного переказу | трейс Tempo зі спанами SQL | «Recent transfer traces», «Service graph» |

## Експеримент 1. Deadlock при зустрічних переказах

**Умови.** Два розрахункові рахунки, одночасно A→B і B→A, пауза 300 мс між блокуванням першого і другого рахунку (`X-Lock-Hold-Ms`), `READ COMMITTED`.

| Режим | Результат (3 пари) | Тривалість |
|---|---|---|
| `naive`: спочатку відправник | 3 × 201, 3 × 409 `deadlock_detected`, `pg_stat_database.deadlocks` +3 | ≈ 1,3 с: 0,3 с паузи + 1 с `deadlock_timeout` |
| `ordered`: менший id першим | 6 × 201, deadlock-ів немає | ≈ 0,6 с: друга транзакція чекає першу |
| `naive` + 3 повтори | 6 × 201 | до 3,4 с через повтори |

**Висновок.** Deadlock виникає через різний порядок захоплення блокувань. PostgreSQL знаходить цикл очікування через `deadlock_timeout` і скасовує одну транзакцію, тому клієнт чекає щонайменше 1 с. Надійне рішення: єдиний порядок блокування (за id). Повтори приховують проблему від клієнта, але збільшують затримку і навантаження. У журналі PostgreSQL видно обидва процеси і рядки, на яких вони чекали.

## Експеримент 2. Втрачене оновлення і рівні ізоляції

**Умови.** 6 одночасних переказів по 100 грн з одного рахунку, пауза 150 мс між читанням і записом.

| Блокування | Ізоляція | Результат | Зміна загальної суми |
|---|---|---|---|
| немає (`none`) | READ COMMITTED | 6 × 201 | **+400 грн** (гроші з'явились нізвідки) |
| немає | REPEATABLE READ | 1 × 201, 5 × 409 `serialization_failure` | 0 |
| немає | SERIALIZABLE | 1 × 201, 5 × 409 `serialization_failure` | 0 |
| `FOR UPDATE` (`ordered`) | READ COMMITTED | 6 × 201 | 0 |

**Висновок.** `READ COMMITTED` сам по собі не захищає від втраченого оновлення, якщо застосунок читає баланс і записує обчислене значення. Варіанти захисту: блокування рядка `FOR UPDATE` (усі перекази проходять, вони просто стають послідовними) або вищий рівень ізоляції (база скасовує конфліктні транзакції, і їх треба повторювати). Для переказів обрано `READ COMMITTED` + `FOR UPDATE` у фіксованому порядку: найменше відмов і немає deadlock-ів. `SERIALIZABLE` залишено для демонстрації.

Обмеження `CHECK (balance >= 0)` не ловить втрачене оновлення, бо баланс залишається додатним. Тому додано метрику загальної суми та алерт `TotalBalanceChanged`.

## Експеримент 3. Антифрод

Сценарій `fraud`: 6 переказів з одного рахунку на різні рахунки, два цикли «пінг-понгу» між іншою парою, потім переказ 95 % балансу.

| Переказ | Правила | Бал | Рішення |
|---|---|---|---|
| 1–4 серії | — або `fan_out` | 0–25 | clean |
| 5–6 серії | `velocity` + `fan_out` | 60 | suspicious |
| 4-й «пінг-понг» | `ping_pong` (2 зворотні) | 60 | suspicious |
| виведення балансу | `round_amount`, `balance_drain`, `velocity`, `fan_out` | 95 | suspicious, **рахунок заблоковано** |
| наступний переказ | — | — | 403 `account_blocked` |

Аналіз одного переказу в локальному прогоні тривав у середньому близько 30 мс, а без черги рішення з'являється за частки секунди після COMMIT. Оскільки переказ уже виконано до аналізу, система блокує подальші операції, а не сам перший підозрілий переказ. Для банку це компроміс між швидкістю і повнотою; синхронна перевірка лише великих сум могла б доповнити схему.

## Архітектурні рішення

| Питання | Варіанти | Рішення | Причина |
|---|---|---|---|
| Як не втратити подію, якщо RabbitMQ недоступний | транзакційний Outbox; публікація після COMMIT + перевірка `pending` | публікація після COMMIT + sweeper | простіше; ціна: перевірка запізнюється до 60 с |
| Чи перевіряти синхронно | у тій самій транзакції; окремий воркер | окремий воркер через брокер | переказ не чекає аналізу, сервіси масштабуються окремо |
| Порядок блокування | за запитом; за id; `NOWAIT` | за id | усуває deadlock без відмов клієнту |
| Де рахувати частоту операцій | у пам'яті воркера; Redis; PostgreSQL | PostgreSQL з індексом `(from_account_id, created_at)` | дані вже в базі, результат не губиться при перезапуску воркера |
| Збір логів | Promtail; Grafana Alloy | Alloy | Promtail застарів, Alloy є його наступником від Grafana |
| Мова сервісів | Python; C# | C# (.NET 8) | вимога до проєкту; строга типізація, `decimal` для грошей |
| Гроші | `double`; `decimal` / `NUMERIC(14,2)` | `decimal` і `NUMERIC` | точні копійки без похибок округлення |

## Обмеження навчальної версії

| Обмеження | Як виправити в реальній системі |
|---|---|
| Секрет JWT і паролі в `docker-compose.yml` | Docker secrets або сховище секретів |
| HTTP без TLS | зворотний проксі з HTTPS |
| Один екземпляр кожного сервісу | кілька екземплярів, балансувальник; воркери вже безпечні для паралельної роботи завдяки `FOR UPDATE` |
| Перевірка після переказу | синхронна перевірка великих сум або затримка зарахування |
| Немає ідемпотентного ключа переказу | заголовок `Idempotency-Key`, щоб повтор запиту клієнтом не створив другий переказ |
| Правила без машинного навчання | модель на історії `transfers` і `fraud_alerts` |

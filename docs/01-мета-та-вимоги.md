# 1. Мета та вимоги

## Відповідність завданню курсу

Завдання: система забезпечує отримання даних про роботу з базою даних, відображає їх через Grafana та використовує Prometheus для збору й обробки метрик. Доступ до системи можливий лише для авторизованих користувачів.

Тема: **Банківські перекази та антифрод-аналіз.** Перекази коштів між рахунками з транзакційністю (ACID) і фоновою перевіркою на шахрайство.

| № | Вимога завдання | Реалізація |
|---|---|---|
| 0 | СУБД у Docker-контейнері | PostgreSQL 16, сервіс `postgres` |
| 1 | Генерація та актуалізація даних у БД програмними засобами | `transfer-service` (C#, Npgsql), `load-generator` (C#) |
| 2 | Збір даних через Prometheus | `postgres-exporter`, метрики сервісів (prometheus-net), метрики RabbitMQ |
| 3 | Зберігання в Time Series Storage | вбудована TSDB Prometheus, зберігання 7 днів |
| 4 | Відображення в Grafana | дашборд «Bank Transfers & Anti-Fraud», 32 панелі в 7 розділах |
| 5 | Дослідження логів через Grafana Loki | Loki + Grafana Alloy, JSON-логи сервісів і журнал PostgreSQL |
| 6 | Дослідження трейсів через Grafana Tempo | Tempo + OpenTelemetry .NET, граф сервісів |
| 7 | Сервер авторизації (SQLite) | `auth-service` на C# і SQLite, токени JWT, ролі |
| 8 | Контейнеризація Docker | усі компоненти в Docker Compose |
| 9 | Обмін повідомленнями між сервісами | RabbitMQ: подія `TransferInitiated` |

Завдання пропонує сервер авторизації на Python 3. За погодженням використано C#, щоб увесь застосунок був на одній платформі; сховище користувачів, як і вимагає завдання, SQLite.

## Бачення (корисність)

**Назва:** Інформаційна система банківських переказів і антифрод-аналізу.

**Проблема.** Перекази між рахунками мають бути атомарними: гроші не можуть зникнути або з'явитись нізвідки, навіть коли багато операцій виконуються одночасно. Паралельні транзакції створюють блокування, взаємоблокування (deadlock) і конфлікти серіалізації, які важко помітити без моніторингу. Шахраї використовують серії дрібних переказів, «прокручування» коштів між рахунками та швидке виведення балансу. Якщо перевіряти все це синхронно, переказ стає повільним.

**Кому потрібна система:**

| Учасник | Тип | Що отримує |
|---|---|---|
| Операціоніст (operator) | основна дійова особа | швидко виконує перекази, бачить причину відмови |
| Аналітик антифроду (analyst) | основна дійова особа | бачить підозрілі перекази, правила, логи і трейси |
| Адміністратор (admin) | допоміжна дійова особа | керує користувачами, розблоковує рахунки, стежить за сервісами |
| Клієнт банку | зацікавлена особа | гроші не губляться, шахрайські операції блокуються |

**Користь.** Переказ виконується одразу, а антифрод-аналіз іде паралельно і не сповільнює його. Цілісність грошей гарантує база даних. Проблеми з транзакціями та підозрілі операції видно на графіках і в алертах.

## Оцінка ефекту від впровадження (лекція 10)

**Усі числа умовні.** Це приклад для невеликого банківського відділення, у реальному проєкті їх треба замінити фактичними даними.

| Показник | Значення |
|---|---|
| Переказів за день | 5 000 |
| Частка шахрайських | 0,1 % (5 переказів) |
| Середня сума шахрайського переказу | 20 000 грн |
| **Втрати без системи за місяць (30 днів)** | 5 × 20 000 × 30 = 3 000 000 грн |
| Частка, яку виявляє і блокує система | 40 % |
| Збережено за місяць | 1 200 000 грн |
| Витрати на обслуговування за місяць | 60 000 грн |
| **Чистий ефект за місяць** | 1 140 000 грн |

Програмне забезпечення відкрите, ліцензійних платежів немає.

## Порівняння з існуючими рішеннями (лекція 3)

| Варіант | Переваги | Недоліки для нашої задачі |
|---|---|---|
| Ручна перевірка виписок | не потребує розробки | запізнюється на години, не масштабується |
| Синхронна перевірка всередині переказу | простий код | переказ чекає на аналіз, збій аналізу зупиняє перекази |
| Готові AML/антифрод-платформи (наприклад, SAS Fraud Management, Feedzai) | машинне навчання, готові правила | висока вартість, закрита будова, довге впровадження |
| **Власна система** | лише потрібні правила, відкритий код, повний моніторинг | правила прості, без машинного навчання |

Для реального банку готова платформа буде доцільнішою. Власну систему обрано, бо мета роботи полягає у проєктуванні мікросервісної архітектури та дослідженні роботи СУБД.

## Функціональні вимоги

| № | Вимога |
|---|---|
| ФВ-1 | Користувач входить через сервер авторизації й отримує токен JWT із роллю |
| ФВ-2 | Адміністратор реєструє, вимикає та вмикає користувачів |
| ФВ-3 | Система показує рахунки, історію переказів і статистику |
| ФВ-4 | Операціоніст відкриває новий рахунок |
| ФВ-5 | Переказ списує кошти з рахунку A і нараховує на рахунок B в одній транзакції (ACID) |
| ФВ-6 | Переказ відхиляється, якщо недостатньо коштів, рахунку немає, рахунок заблоковано, валюти різні або сума некоректна |
| ФВ-7 | Рівень ізоляції (`READ COMMITTED`, `REPEATABLE READ`, `SERIALIZABLE`) і спосіб блокування задаються налаштуванням або заголовком запиту |
| ФВ-8 | Deadlock і конфлікт серіалізації розпізнаються, транзакція відкочується, можливий повтор |
| ФВ-9 | Після фіксації переказу подія `TransferInitiated` надсилається в RabbitMQ |
| ФВ-10 | fraud-worker аналізує частоту операцій і нараховує бал ризику за правилами |
| ФВ-11 | Підозрілі перекази отримують статус `suspicious`, правила записуються в `fraud_alerts` |
| ФВ-12 | Рахунок із балом ризику 80 і більше автоматично блокується, розблокувати може лише адміністратор |
| ФВ-13 | Перекази, подія яких не надійшла, перевіряються пізніше (sweeper) |
| ФВ-14 | Повторна доставка події не обробляється двічі, зіпсовані події переходять у `transfers.invalid` |
| ФВ-15 | Система збирає метрики переказів, транзакцій, антифроду, авторизації, PostgreSQL і RabbitMQ |
| ФВ-16 | Grafana показує метрики, логи і трейси на одному дашборді |
| ФВ-17 | Алерти на deadlock-и, конфлікти серіалізації, повільні транзакції, зміну загальної суми грошей, шахрайство, збої сервісів |
| ФВ-18 | Логи всіх сервісів і PostgreSQL доступні в Loki, з переходом до трейсу |
| ФВ-19 | Шлях переказу через усі сервіси доступний як трейс у Tempo |
| ФВ-20 | Генератор навантаження створює типові, помилкові, шахрайські та конкурентні сценарії |

## Межі проєкту (лекція 11)

**Входить:** авторизація з ролями, рахунки, перекази в транзакціях, дослідження рівнів ізоляції та deadlock-ів, подія в брокері, правила антифроду, блокування рахунків, метрики, логи, трейси, алерти, генератор навантаження.

**Не входить:**

| Функція | Причина виключення |
|---|---|
| Конвертація валют | окрема підсистема курсів, не потрібна для дослідження транзакцій |
| Міжбанківські перекази (SWIFT, SEP) | потребують зовнішніх систем |
| Машинне навчання в антифроді | для навчального проєкту достатньо правил |
| Інтернет-банкінг для клієнтів | у системі працюють лише співробітники банку |

### Детальний: «Виконати переказ»

| Поле | Значення |
|---|---|
| Дійова особа | Операціоніст |
| Мета | Перемістити кошти з рахунку A на рахунок B |
| Передумова | Користувач має токен із роллю `operator` або `admin`, PostgreSQL працює |
| Основний потік | Операціоніст надсилає рахунки та суму; система перевіряє дані, блокує обидва рахунки, перевіряє баланс, змінює баланси, записує переказ, фіксує транзакцію, надсилає подію; повертає 201 |
| Альтернативний потік | Недостатньо коштів або різні валюти: 422. Рахунок заблоковано: 403. Рахунку немає: 404. Некоректна сума: 400. Немає токена: 401. Неправильна роль: 403 |

### Детальний: «Перевірити переказ на шахрайство»

| Поле | Значення |
|---|---|
| Дійова особа | fraud-worker |
| Мета | Оцінити ризик переказу |
| Передумова | У черзі `transfers.fraud-check` є подія |
| Основний потік | Сервіс читає подію, блокує запис переказу, рахує кількість переказів, отримувачів і зворотних переказів у вікнах часу, нараховує бал, записує результат, підтверджує повідомлення |

## Чому RabbitMQ, а не Kafka

| Критерій | RabbitMQ | Kafka |
|---|---|---|
| Завдання проєкту | черга завдань: кожну подію перевіряє один воркер | потік подій для багатьох споживачів |
| Підтвердження обробки | вбудоване (ack/nack), dead-letter | через зсув (offset) |
| Простота запуску | один контейнер із веб-панеллю | складніше налаштування |
| Метрики | вбудований плагін Prometheus | потребує окремого експортера |
